# Analysis: Token Optimization and Usage in the Admin Dashboard

Status: proposed
Scope: analyzed at commit `085059d0` on 2026-11-16; integration points and schemas
revalidated at commit `4946962c` on 2026-11-17
Audience: maintainers and contributors

This document assesses whether ModelGlot can expose RTK and Headroom
optimization activity, model-level token usage, and context utilization in a new
read-only Admin tab.

The conclusion is that the feature is feasible, but the requested information
must not be presented as one homogeneous measurement. RTK and Headroom own
optimization ledgers outside ModelGlot, while ModelGlot owns provider usage and model
context metadata but does not currently persist request-level token usage.

The proposed implementation is split into an immediately useful external-tool
summary and a later durable usage pipeline. The detailed execution sequence is
documented in
[`token-optimization-admin-implementation-plan.md`](token-optimization-admin-implementation-plan.md).

Related: [`../CONTRIBUTING.md`](../CONTRIBUTING.md) for the quality gate that any
change described here must satisfy.

---

## 1. Problem Statement

ModelGlot can install and configure RTK and Headroom for supported coding agents.
The installer advertises token savings of up to 90%, but the Admin dashboard does
not currently show:

1. whether RTK or Headroom is installed and active;
2. how many tokens the tools report as saved;
3. which models process the requests;
4. how many input, output, cache, and reasoning tokens are used;
5. how much of a model's context window is used;
6. whether the optimization and usage figures can be combined safely.

The requested outcome is a transparent operational view that helps a user
understand how efficiently the project consumes model tokens and context.

### 1.1 Terminology

The product should use **token and context optimization**, not “network traffic
optimization.” RTK and Headroom reduce model payloads and tool output; they do
not optimize TCP traffic or provider bandwidth.

The UI must also distinguish these concepts:

| Concept | Meaning | Existing owner |
| --- | --- | --- |
| Original token count | Size before an optimization | RTK or Headroom |
| Optimized token count | Size after an optimization | RTK or Headroom |
| Provider input tokens | Tokens billed or reported for a model request | Provider, observed by ModelGlot |
| Provider output tokens | Tokens generated by a model | Provider, observed by ModelGlot |
| Context window | Maximum context supported by a model | Provider metadata and ModelGlot catalog |
| Context occupancy | Context currently retained by a conversation | Coding agent; partially stored by ModelGlot |

## 2. Executive Summary

### 2.1 Feasibility verdict

| Capability | Feasibility | Conclusion |
| --- | --- | --- |
| New read-only Admin tab | High | The Admin navigation, HTML views, routing, API, and security patterns already support this shape. |
| RTK savings summary | High | RTK 0.44.2 exposes `rtk gain --format json`. |
| Headroom savings summary | High | Headroom 0.40.0 exposes `headroom savings --json`. |
| Tool availability and versions | High | Both tools expose version commands and can be resolved through `PATH`. |
| Historical optimization timeline | Medium | Depends on the stable JSON schema of each external tool and its own retention rules. |
| Exact per-model provider usage | Medium-high | Usage events exist in DEBUG traces, but provider/model attribution and persistence are incomplete. |
| Historical context utilization | Medium | Model context limits are known; current Codex session occupancy is stored; regular API request history is not. |
| Combined exact savings across RTK and Headroom | Low without qualification | The ledgers have different bases and may overlap. |

### 2.2 Recommended delivery

1. **Wave 1:** Add a read-only Admin view that imports the RTK and Headroom
   summaries through their JSON commands.
2. **Wave 2:** Normalize and persist ModelGlot provider usage, then add per-model
   request, token, and context aggregates.
3. **Wave 4:** Add trends, optional cost estimates, and export after the
   measurement semantics are stable.

This sequence gives users immediate visibility without presenting estimates or
foreign ledgers as ModelGlot billing data.

### 2.3 Main architectural finding

ModelGlot cannot independently calculate RTK or Headroom savings. Both tools modify
content before ModelGlot receives the request. ModelGlot sees the optimized result but not
the original content. Therefore, a correct dashboard must import the tools'
own measurements and preserve their provenance.

Conversely, ModelGlot is the correct owner of provider request usage and model
attribution. RTK statistics cannot provide that information because RTK acts on
shell command output before a model is selected, and Headroom's model attribution
may be `unknown` unless the upstream MCP process receives a model hint.

## 3. Current RTK and Headroom Integration

### 3.1 Installation and agent configuration

ModelGlot does not contain an RTK or Headroom request runtime. The installers add the
tools and configure the selected coding agents:

| Element | Location | Behavior |
| --- | --- | --- |
| Pinned RTK version | `scripts/install.ps1:32`–`:36` | RTK `0.44.2`, with a pinned SHA-256 on Windows |
| Pinned Headroom version | `scripts/install.ps1:33` | `headroom-ai[mcp]==0.40.0` |
| RTK installation | `scripts/install.ps1:702`–`:751` | Installs the verified executable under `~/.local/bin` |
| RTK verification | `scripts/install.ps1:753`–`:820` | Runs `--version` and `gain` with telemetry disabled |
| RTK agent configuration | `scripts/install.ps1:834`–`:855` | Claude, Codex, and Pi receive `rtk init` configuration |
| Headroom installation | `scripts/install.ps1:857`–`:880` | Installs the `headroom` command through `uv tool` |
| Headroom agent registration | `scripts/install.ps1:882`–`:903` | Registers the MCP server for Claude, Codex, and Grok |

The POSIX installer follows the same behavior in `scripts/install.sh`.

This separation has three consequences:

1. The Admin server can inspect the tools, but it does not control whether an
   agent invokes them.
2. RTK and Headroom statistics may exist even when ModelGlot has not served a request.
3. Conversely, an ModelGlot request may not have an RTK or Headroom optimization
   record.

### 3.2 RTK operating model

RTK is a command-output optimizer. Its Claude integration installs a
`PreToolUse` Bash hook that rewrites supported commands to their RTK
equivalents. RTK therefore reduces the tool-result payload later included in a
model request.

Available statistics include:

```text
rtk gain
rtk gain --history
rtk gain --daily
rtk gain --weekly
rtk gain --monthly
rtk gain --all
rtk gain --format json
```

The JSON summary observed with RTK 0.44.2 has this shape:

```json
{
  "summary": {
    "total_commands": 29,
    "total_input": 19009,
    "total_output": 10289,
    "total_saved": 8720,
    "avg_savings_pct": 45.87300752275238,
    "total_time_ms": 115223,
    "avg_time_ms": 3973
  }
}
```

The observed values demonstrate that the data is locally available and already
aggregated. The JSON summary is aggregate-only and does not provide reliable
per-model attribution: RTK operates before model selection.

A machine-readable daily timeline is already available with:

```text
rtk gain --daily --format json
```

The observed RTK 0.44.2 response extends the summary with a `daily` array:

```json
{
  "summary": {
    "total_commands": 29,
    "total_input": 19009,
    "total_output": 10289,
    "total_saved": 8720,
    "avg_savings_pct": 45.87300752275238,
    "total_time_ms": 115223,
    "avg_time_ms": 3973
  },
  "daily": [
    {
      "date": "2026-11-12",
      "commands": 10,
      "input_tokens": 8059,
      "output_tokens": 2910,
      "saved_tokens": 5149,
      "savings_pct": 63.89130165032883,
      "total_time_ms": 1720,
      "avg_time_ms": 172
    }
  ]
}
```

This makes an RTK daily trend measurable without modelglot-side persistence. The
`--history --format json` probe on the same version returned only the summary
shape, so the implementation must not depend on undocumented per-command
history fields. Raw command/project history is excluded from the Admin API
regardless of the upstream command's output.

### 3.3 Headroom operating model

Headroom is installed as an MCP server. In the configured environment it
compresses context in the agent process and writes durable savings events to its
own ledger. ModelGlot does not start the separate Headroom proxy, so proxy-only
statistics are not an ModelGlot data source.

The supported reporting command is:

```text
headroom savings --json
```

The JSON schema observed with Headroom 0.40.0 includes:

```json
{
  "schema_version": 2,
  "top_model": "unknown",
  "lifetime": {
    "tokens_saved": 0,
    "tokens_before": 0,
    "cost_usd": 0.0,
    "cost_effective_usd": 0.0,
    "basis": "list",
    "calls": 0,
    "savings_percent": 0.0,
    "new_input_tokens": 0,
    "new_input_savings_percent": 0.0
  },
  "windows": {
    "today": {},
    "last_7_days": {},
    "last_30_days": {}
  },
  "by_model": [],
  "by_client": []
}
```

Important semantics:

- The live Headroom 0.40.0 response also contains a top-level `path` field.
  ModelGlot must strip it and must not expose the private ledger location through the
  Admin API.
- Headroom retains durable savings data for a bounded period, with the current
  CLI allowing a lookback of up to 30 days.
- `tokens_before` and `tokens_saved` describe Headroom's compression operation.
- `cost_usd` is a price-list estimate, not an invoice reconciliation.
- `top_model` and `by_model` can be `unknown` because the MCP process does not
  necessarily know which model the agent ultimately selects.
- A zero report means “no recorded Headroom savings,” not necessarily “Headroom
  is not installed” or “Headroom never ran.”

### 3.4 External-tool measurement boundary

| Fact | RTK | Headroom |
| --- | --- | --- |
| Owns original-vs-optimized baseline | Yes | Yes |
| Owns provider request usage | No | No |
| Reliable per-model attribution | No | Conditional; may be unknown |
| Owns command/client breakdown | Command-oriented | Client/model-oriented when known |
| Provides machine-readable output | Yes | Yes |
| Telemetry is not required for local stats | Yes | Yes for the local ledger |

The Admin implementation must import the aggregate reports through the
documented JSON commands instead of depending on private ledger paths or JSONL
schemas. A private-file reader would be more fragile and would couple ModelGlot to
tool internals.

## 4. Current ModelGlot Usage Instrumentation

### 4.1 Request outcomes

`RequestOutcomeMiddleware` creates one request-scoped outcome and emits a final
`request.completed` INFO log containing:

- wire API;
- provider id;
- model;
- status code;
- success, failure, or cancellation;
- duration;
- failure reason.

Evidence: `src/free_claude_code/api/request_outcomes.py:41`–`:134` and
`src/free_claude_code/core/request_outcomes.py:9`–`:38`.

The outcome is durable only in the log file. It is not written to SQLite and is
not exposed by an Admin endpoint.

### 4.2 Provider usage events

Provider usage is observed at the provider boundary. `SourceRecoveryState.observe`
emits a `provider.attempt.usage` DEBUG trace containing the raw upstream usage
payload:

```python
trace_event(
    stage="provider",
    event="provider.attempt.usage",
    source="provider",
    request_id=self._execution.request_id,
    execution_id=self._execution.execution_id,
    attempt=self._execution.attempts_started,
    usage=usage,
)
```

Evidence: `src/free_claude_code/providers/continuation.py:68`–`:90`.

Current limitations:

1. The usage event does not include provider, gateway model, or downstream model.
2. Anthropic Messages can emit separate input and output usage events.
3. Gemini `usageMetadata` is not captured by the current observer.
4. OpenAI Chat cache tokens are present in the client payload but are not
   included in the debug usage payload.
5. DEBUG traces are excluded at the default INFO log level.
6. Retry and continuation attempts need an explicit aggregation policy.

The provider request trace already contains the missing routing identity:

- provider;
- request id;
- execution id;
- gateway model;
- downstream model.

Evidence: `src/free_claude_code/providers/attempt_loop/loop.py:125`–`:137`.

The implementation should enrich the usage observation at its source rather
than reconstructing model identity later from log files.

### 4.3 Request-side estimates

ModelGlot estimates input tokens before provider execution for Anthropic Messages,
Responses, Gemini, and Chat Completions. These estimates support client-facing
usage and local-provider context guards; they are not provider-confirmed usage.

Evidence: `src/free_claude_code/application/execution.py:139`–`:354` and
`src/free_claude_code/api/handlers/token_count.py:56`–`:84`.

The dashboard must label estimated and provider-reported values differently.
A provider-reported token count and a pre-flight estimate must never be summed
as if they describe the same quantity.

### 4.4 Durable storage

ModelGlot owns one SQLite database at the configured ModelGlot database path. The database
is initialized and migrated transactionally:

- `src/free_claude_code/runtime/bootstrap.py:82`–`:94`;
- `src/free_claude_code/runtime/sqlite_database.py:139`–`:190`;
- `src/free_claude_code/runtime/sqlite_migrations/__init__.py:1`–`:25`.

The current schema is version 5 and contains Code and messaging tables. The
schema guard in `runtime/sqlite_database.py:24`–`:90` requires every new table
to be registered explicitly. A usage table therefore requires both a new
migration and a schema-guard update.

### 4.5 Context metadata and occupancy

Model context metadata is already available:

- `CatalogModel.context_window_tokens` and `max_output_tokens` at
  `src/free_claude_code/application/model_catalog.py:31`–`:43`;
- client-safe context resolution at
  `src/free_claude_code/application/model_catalog.py:53`–`:58`;
- provider metadata projection at
  `src/free_claude_code/application/model_catalog.py:160`–`:163`.

Codex Code sessions already persist their current cumulative context
occupancy:

- model field: `src/free_claude_code/application/code_sessions/models.py:38`;
- protocol event: `src/free_claude_code/runtime/codex_protocol.py:60`–`:78`;
- persistence: `src/free_claude_code/runtime/code_sessions_sqlite.py:214`–`:244`.

This value is useful but has different semantics from request input tokens. The
Admin view must not present it as a per-request metric.

## 6. Measurement Semantics

### 6.1 Four distinct metric families

The dashboard should contain four visually distinct families:

1. **Tool-reported optimization savings**
   - Source: RTK and Headroom JSON reports.
   - Basis: original versus optimized content observed by each tool.
   - Unit: tool-estimated tokens.
2. **Provider-reported request usage**
   - Source: upstream provider usage payloads.
   - Basis: model request/response usage.
   - Unit: provider-reported tokens.
3. **Request-side estimates**
   - Source: ModelGlot tokenizer estimation.
   - Basis: pre-flight request size.
   - Unit: estimated tokens.
4. **Context capacity and occupancy**
   - Source: model catalog and coding-agent context events.
   - Basis: context-window capacity and current conversation occupancy.
   - Unit: tokens or percentage of a known limit.

### 6.2 Non-additivity

RTK and Headroom savings must not be displayed as a single exact total without
a caveat. The reasons are:

- the tools may optimize different content;
- their baselines may overlap;
- Headroom can report input-token and cost transformations that are not
  directly comparable with RTK command-output savings;
- RTK savings occur before model selection and cannot be assigned to a model;
- Headroom model attribution may be unknown;
- provider usage includes output and reasoning tokens that optimization reports
  do not cover.

A combined figure may be shown only if it is explicitly labeled as an
**upper-bound estimate of tool-reported savings** and never as measured billing
savings.

### 6.3 Request accounting policy

The durable usage implementation must define one final accounting unit before
writing the schema. The recommended policy is:

- persist one row per client request;
- attribute tokens to the provider/model that delivered the successful
  response;
- include failed attempts in attempt counters but not in successful model token
  totals unless the provider explicitly reports usage for them;
- preserve a separate `attempts` count and duration;
- identify fallback and continuation attempts without counting their usage twice;
- distinguish provider-reported tokens from ModelGlot estimates.

The exact policy must be encoded in tests and in the API schema version.

## 7. Proposed Architecture

### 7.1 Read-only Admin view

Add a dedicated view named **Token optimization** with route:

```text
/admin/token_optimization
```

The view should contain:

1. a summary row for RTK and Headroom availability;
2. a separate savings card for each tool;
3. a model/provider usage table;
4. a context utilization table;
5. a methodology and limitations panel.

The global Apply bar remains hidden because the view does not change
configuration.

### 7.2 External-tool collection

Use a runtime-owned collector that:

- resolves the executable with `shutil.which`;
- invokes it directly with an argument list, never through a shell;
- sets `RTK_TELEMETRY_DISABLED=1` for RTK;
- applies a short timeout;
- captures stdout and stderr separately;
- parses JSON only after a successful exit;
- validates the result into typed application models;
- converts absence, timeout, malformed output, and tool errors into separate
  non-fatal states;
- never logs command output that may contain user content.

The tool report should be read when the Admin view requests it, with a short
server-side cache to prevent repeated subprocess execution from several browser
clients or refresh cycles.

### 7.3 Suggested API boundaries

The first implementation can expose one aggregate endpoint:

```text
GET /admin/api/token-optimization
```

Suggested response shape:

```json
{
  "schema_version": 1,
  "generated_at": "2026-11-16T20:00:00Z",
  "optimizations": {
    "rtk": {
      "state": "available",
      "version": "0.44.2",
      "source": "rtk gain --format json",
      "basis": "tool_reported",
      "total_commands": 29,
      "tokens_before": 19009,
      "tokens_after": 10289,
      "tokens_saved": 8720,
      "savings_percent": 45.87
    },
    "headroom": {
      "state": "available",
      "version": "0.40.0",
      "source": "headroom savings --json",
      "basis": "tool_reported",
      "tokens_saved": 0,
      "tokens_before": 0,
      "calls": 0,
      "savings_percent": 0.0,
      "model_attribution": "unknown"
    }
  },
  "usage": {
    "state": "not_collected",
    "models": []
  },
  "notices": []
}
```

The durable usage phase can add a separate endpoint:

```text
GET /admin/api/usage?from=<timestamp>&to=<timestamp>&group_by=model
```

Separating the endpoints prevents a slow historical query from delaying the
external-tool summary and allows the UI to refresh each section independently.

### 7.4 Canonical provider usage record

The durable phase should normalize every protocol into one record:

| Field | Meaning |
| --- | --- |
| `request_id` | Stable client request id |
| `execution_id` | Provider execution id |
| `attempt` | Attempt ordinal within the execution |
| `provider_id` | ModelGlot provider id |
| `gateway_model` | Model selected by the client |
| `provider_model` | Model sent to the provider |
| `wire_api` | Messages, Responses, Chat, or Gemini |
| `input_tokens` | Provider-reported input tokens |
| `output_tokens` | Provider-reported output tokens |
| `cache_read_tokens` | Cache reads, when reported |
| `cache_creation_tokens` | Cache writes, when reported |
| `reasoning_tokens` | Reasoning tokens, when separately reported |
| `total_tokens` | Provider total when reported |
| `estimated_input_tokens` | ModelGlot pre-flight estimate, when available |
| `outcome` | Success, failure, or cancellation |
| `status_code` | HTTP status |
| `duration_ms` | Request duration |
| `failure_reason` | Sanitized failure category |
| `created_at` | UTC event timestamp |

Unknown values must remain `null`. They must not be converted to zero unless
the aggregation explicitly treats “unknown” as “not reported.”

### 7.5 Durable schema proposal

The next migration is expected to be `v0006_usage_events.py`. A proposed table
is:

```sql
CREATE TABLE usage_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    request_id TEXT,
    execution_id TEXT,
    attempt INTEGER NOT NULL DEFAULT 1,
    provider_id TEXT NOT NULL,
    gateway_model TEXT,
    provider_model TEXT,
    wire_api TEXT NOT NULL,
    outcome TEXT NOT NULL,
    status_code INTEGER,
    duration_ms REAL,
    failure_reason TEXT,
    input_tokens INTEGER,
    output_tokens INTEGER,
    cache_read_tokens INTEGER,
    cache_creation_tokens INTEGER,
    reasoning_tokens INTEGER,
    total_tokens INTEGER,
    estimated_input_tokens INTEGER,
    created_at INTEGER NOT NULL
);
```

Recommended indexes:

```text
(created_at)
(provider_id, provider_model, created_at)
(gateway_model, created_at)
(request_id)
```

The final migration shape must be reviewed against the project's retention and
database-size policies before implementation. A retention job may be required
if usage rows grow without bound.

### 7.6 Context utilization

For each request, the dashboard can calculate:

```text
request_input_ratio = input_tokens / context_window_tokens
```

Only when the context window is provider-confirmed and present. Unknown or
default context metadata must not be rendered as an authoritative utilization
percentage.

For Code sessions, the existing `context_used_tokens` field can provide a
current-occupancy indicator. It must be labeled separately from request input
utilization and should not be aggregated into the same average without a clear
definition.

- tool not installed;
- tool installed but no statistics;
- tool timeout;
- tool output incompatible with the expected schema;
- Headroom model attribution unknown;
- no ModelGlot usage rows yet;
- usage rows available;
- database unavailable;

### 8.3 Wording

Recommended labels:

- “Tool-reported tokens saved”;
- “Provider-reported input tokens”;
- “Estimated input tokens”;
- “Model context limit”;
- “Current Code session context”;
- “Approximate list-price cost”.

Avoid:

- “tokens billed” unless the source is an invoice;
- “money saved” without a price source and estimate label;
- “traffic saved” when the metric is tokens;
- “model X saved N tokens” for RTK;
- a combined RTK/Headroom exact total.

## 9. Privacy and Security

1. The Admin API remains loopback-only through `require_loopback_admin`.
2. External commands must not receive shell interpolation, user-controlled
   arguments, or secrets.
3. `rtk gain --history` is excluded from the default Admin response because it
   can expose command and project details.
4. Headroom ledger paths are not displayed by default.
5. No request body, prompt, command output, or credential is persisted in the
   usage table.
6. Provider and model ids are operational metadata, but they can still reveal
   customer-specific routing. The database inherits the existing ModelGlot database
   permissions and local storage policy.
7. Admin API responses use the existing `Cache-Control: no-store` policy.
8. The collector sets `RTK_TELEMETRY_DISABLED=1`; it must not enable telemetry
   merely to collect local statistics.

## 10. Failure Modes and Mitigations

| Failure | Impact | Mitigation |
| --- | --- | --- |
| RTK or Headroom is absent | No tool summary | Render an explicit unavailable state; do not fail the page |
| A tool times out | Partial summary | Return the other tool and a non-fatal notice |
| JSON schema changes | Missing fields | Validate required fields and degrade to an empty summary with a warning |
| RTK has no per-model data | No model-level optimization attribution | Explain that RTK operates before model selection |
| Headroom model is `unknown` | No reliable model savings | Show aggregate savings and label attribution unknown |
| Provider omits usage | Unknown token values | Preserve nulls and show “not reported” |
| Gemini usage is missed | Under-counting | Add Gemini normalization before enabling the durable total |
| Retries create duplicate totals | Over-counting | Define and test final-request accounting |
| Database write fails | Lost metrics, request still succeeds | Best-effort telemetry; never fail generation |
| Database grows indefinitely | Disk pressure | Add retention and a storage-size limit |
| Context limit is a catalog fallback | Misleading percentage | Omit utilization when the limit is not provider-confirmed |
| Tool and provider figures are combined | Misleading total | Keep separate cards and disclose non-additivity |
| Admin request overlaps the tool collector | Duplicate subprocesses | Cache the result and coalesce concurrent refreshes |

## 11. Risks

### 11.1 External-tool coupling

ModelGlot would depend on the CLI output of tools it installs but does not own.

Mitigation: use the documented JSON commands, version the Admin response schema,
keep parsers tolerant, and treat every tool as optional. Do not import private
ledger files or upstream source modules.

### 11.2 Meaning of “savings”

A token saved before a request is not necessarily a provider bill avoided.
Caching, provider accounting rules, and output pricing can change the economic
effect.

Mitigation: prioritize token counts over currency and label currency as an
approximate list-price estimate.

### 11.3 Request-path overhead

Persisting a row for every request can affect latency and storage.

Mitigation: use the existing asynchronous SQLite writer, keep aggregation in
memory where possible, batch writes if measurements show contention, and make
telemetry failure non-fatal.

### 11.4 Incorrect model attribution

Fallback and continuation can involve multiple provider attempts.

Mitigation: retain gateway and provider model separately, use the delivered
provider/model for request totals, and retain attempt counts separately.

### 11.5 Schema growth

A request table can grow rapidly.

Mitigation: choose retention before enabling persistent collection, index by
time and model, and expose the storage state in diagnostics.

## 12. Scope Boundaries

### 12.1 In scope

- A dedicated read-only Admin tab.
- RTK and Headroom availability, versions, and aggregate savings.
- Provider/model request and token summaries.
- Context-window limits and clearly defined context utilization.
- Local persistence of minimal usage metadata.
- Time filters, refresh behavior, empty/error states, and optional CSV export.

### 12.2 Out of scope

- Displaying prompts, completions, tool arguments, or raw command output.
- Replacing provider invoices with local estimates.
- Starting or operating the Headroom proxy.
- Changing RTK filters or Headroom compression policies.
- Automatically enabling RTK or Headroom from the Admin dashboard.
- Claiming that RTK and Headroom savings are additive.
- Building a public metrics endpoint or Prometheus exporter in the first
  implementation.
- Changing routing, model selection, fallback behavior, or provider requests.

## 13. Implementation Sequence

The implementation is intentionally staged:

1. **Baseline and contracts:** freeze the observed external JSON semantics and
   define the Admin data contract.
2. **External-tool summary:** collect and display RTK and Headroom aggregates.
3. **Provider usage normalization:** produce one canonical usage record for all
   supported protocols.
4. **Durable storage:** add and maintain a bounded usage table.
5. **Usage and context UI:** add model/provider summaries and utilization.
6. **Hardening and release:** retention, diagnostics, documentation, and full
   quality gates.

Each step, file change, test, acceptance criterion, and effort estimate is
specified in
[`token-optimization-admin-implementation-plan.md`](token-optimization-admin-implementation-plan.md).

## 14. Decisions Required Before Implementation

| Decision | Recommended option | Reason |
| --- | --- | --- |
| View name | Token optimization | Matches the actual unit and avoids network-traffic ambiguity |
| First release scope | RTK + Headroom aggregate summary | Useful immediately without changing the request path |
| External data source | Documented JSON CLI | Avoids coupling to private ledgers |
| Usage storage unit | One final row per client request | Prevents retry double counting |
| Model identity | Gateway model and provider model stored separately | Preserves fallback and routing truth |
| Unknown token values | `null`, never zero | Preserves the difference between unknown and zero |
| Combined RTK/Headroom total | Do not show by default | Sources are not proven additive |
| Cost display | Optional, approximate, off by default | Prices are incomplete and change over time |
| Context utilization | Show only with confirmed context limits | Avoids false precision |
| Retention | Defined before persistent collection | Prevents unbounded local storage |
